# Ошибка высоты ряда ShelfGrid: разбор и подробный план исправления

> **Исполнение:** реализация выполнена через `superpowers:subagent-driven-development`. Отмеченные пункты подтверждены проверками; неполные ручные проверки сохранены открытыми и пояснены в разделе 11.

**Goal:** При раскрытии третьей заметки сохранять первые две в одной колонке, когда их суммарная естественная высота с промежутком помещается в ряд, высоту которого обеспечивает высокая соседняя заметка.

**Architecture:** Сохранить существующие ряды, последовательные стеки и распределение свободной высоты. В `packShelfItems` дополнить условие завершения: прежде чем исключать первую неразмещённую высокую карточку из ряда, проверить упаковку при её высоте и принять результат только при фактическом размещении этой карточки. Общий максимум по всем заметкам группы не используется.

**Tech Stack:** React 19, TypeScript 7, CSS Grid, Vitest 4, Testing Library, ResizeObserver/MutationObserver, Jujutsu. Новые зависимости не требуются.

**Spec:** Требования и критерии приёмки находятся в разделах 5 и 9 этого документа. Они уточняют правило завершения ряда из [спецификации стеков](../specs/2026-09-06-unbounded-note-card-stacking-design.md), сохраняя остальные её ограничения.

**Статус:** исправление реализовано, 17 постоянных регрессионных тестов добавлены, полная suite и сборка прошли. Независимый review не выявил дефектов кода. Браузерное воспроизведение подтвердило основной сценарий, включая промежуточные кадры. Ограничения ручной приёмки и результаты — раздел 11.

## 1. Наблюдаемая проблема и границы доказательства

Пользователь раскрывает подсписок в третьей заметке, `Merc Missions`. Первые две заметки слева до этого стоят друг под другом. Справа находятся две высокие заметки, поэтому первые две продолжают помещаться в одну колонку и после раскрытия. Тем не менее интерфейс перераспределяет карточки так, будто доступной высоты больше нет.

Ожидаемый результат для такой конфигурации: третья карточка использует свободное место внутри своего слота, первые две сохраняют колонку и геометрию, высокие карточки остаются справа в том же ряду.

Исходный референс пользователя: `/Users/kana/Desktop/Screen Recording 2026-09-07 at 16.50.40.mov`. На 2026-09-08 файл по этому пути отсутствует; повторный просмотр записи в этой проверке не состоялся. Ни число CSS-колонок на записи, ни её точные пиксельные размеры здесь не выдаются за измеренные факты. При исполнении необходимо сопоставить исправленный интерфейс с доступной записью либо воспроизведённым исходным состоянием и явно зафиксировать ограничения проверки.

При этом ошибка алгоритма воспроизведена непосредственно вызовом существующего кода на четырёхколоночной искусственной конфигурации, соответствующей описанной взаимосвязи пяти карточек. Это подтверждает дефект независимо от доступности видео. Связь с конкретным браузерным состоянием окончательно проверяется в Task 0 и Task 5.

### Что нужно исправить в предыдущем объяснении

1. Увеличение высоты третьей карточки само по себе не уменьшает предел для размещения первых двух. Прежняя формулировка об этом была ошибочной.
2. Фраза «берутся первые три заметки» верна только для трёх доступных колонок и единичных spans. На четырёх колонках исходная оценка включает первые четыре карточки.
3. В воспроизведении ниже начальная оценка **не меняется вообще**. Меняется промежуточная возможность сложить вторую и третью карточки. Из-за этого высокая пятая карточка перестаёт попадать в первый проход, хотя корректная конечная композиция всё ещё существует.
4. Обычный `buildShelfLayout` вызывает `packShelfItems` напрямую в цикле. `appendTailToComposition` используется в пути расширения редактора; приписывать ему обычный перенос пятой карточки на следующий ряд неверно.
5. Переход на независимые masonry-колонки не нужен: утверждённая модель проекта — общие ряды и стеки с выравниванием нижних границ.

Последовательность вызовов:

```text
Раскрытие секции → aria-expanded / изменение дочерних элементов
  → MutationObserver → scheduleLayout(false)
  → measureNaturalHeights → heightsChanged
  → shouldRepack → buildShelfLayout, если packingFrozen выключен
  → packShelfItems → layoutComposition
  → новые gridColumnStart / gridRowStart / gridRowEnd на живых карточках
```

В [GamePage.tsx](../../../src/pages/GamePage.tsx) `packingFrozen` включается при переносе или редактировании. Обычное раскрытие секции этого ограничения не устанавливает. Само наблюдение реального изменения высоты необходимо и соответствует действующему контракту. Ошибка находится в решении о составе ряда после измерения.

Важно различать естественную высоту карточки и её уже растянутую высоту на экране. После выравнивания две карточки могут выглядеть одинаково высокими, хотя их измеренные естественные высоты различны. Алгоритм принимает решения по естественным высотам.

## 3. Точное воспроизведение на пяти карточках

Используются четыре колонки, единичные spans, промежуток в стеке 6 px и между рядами 12 px. Нумерация карточек в тексте начинается с 1; индексы API — с 0.

| Карточка | До раскрытия | После раскрытия |
| --- | ---: | ---: |
| 1 | 250 | 250 |
| 2 | 300 | 300 |
| 3, раскрываемая | 160 | 210 |
| 4 | 500 | 500 |
| 5 | 600 | 600 |

Проверяемые факты:

```text
Первая + промежуток + вторая = 250 + 6 + 300 = 556 <= 600.
Третья после раскрытия = 210 <= 600.
Начальная оценка в обоих состояниях = max(первые четыре) = 500.
```

Все пять карточек по-прежнему могут занимать один ряд высотой 600:

```text
Колонка 1: [1, 2]    Колонка 2: [3]    Колонка 3: [4]    Колонка 4: [5]
```

### 3.1. Почему свёрнутое состояние случайно работает

Первый проход с `shelfHeight = 500`:

1. `250 + 6 + 300 = 556 > 500`: первые две временно не складываются.
2. Первая карточка занимает первую колонку.
3. `300 + 6 + 160 = 466 <= 500`: вторая и третья временно складываются во второй колонке.
4. Четвёртая занимает третью колонку, пятая — четвёртую. Все пять попали в текущий проход.
5. В `nextShelfHeight` обнаруживается высота пятой карточки: 600. Алгоритм начинает проход заново.
6. При пределе 600 первые две уже складываются: 556 <= 600. Третья к ним не присоединяется: `250 + 6 + 300 + 6 + 160 = 722 > 600`.

Итог: `[1,2] | [3] | [4] | [5]`, один ряд высотой 600.

### 3.2. Почему раскрытие ломает ту же допустимую композицию

Первая оценка всё ещё равна 500:

1. Первые две снова не складываются при этой временной оценке: 556 > 500.
2. Теперь не складываются и вторая с третьей: `300 + 6 + 210 = 516 > 500`.
3. Первые четыре занимают четыре отдельные колонки. Пятая не попадает в проход.
4. `nextShelfHeight` вычисляется **только по этим четырём слотам** и остаётся равным 500.
5. Условие `if (nextShelfHeight <= shelfHeight) break` завершает упаковку, даже не проверив возможность размещения пятой при её собственной высоте 600.
6. `buildShelfLayout` начинает следующий ряд с пятой карточки.

Фактический результат: `[1] | [2] | [3] | [4]`, затем отдельный ряд `[5]`. Общая высота становится `500 + 12 + 600 = 1112`.

## 4. Корневая ошибка и пробел в тестах

Упаковщик попадает в круговую зависимость: чтобы учесть высокую пятую карточку, он должен сначала освободить для неё колонку; чтобы освободить колонку за счёт первых двух карточек, ему уже нужна высота пятой.

Повторный проход решает эту зависимость только тогда, когда высокая карточка каким-то образом уже была допущена на предыдущем проходе. Прекращение роста максимума **внутри выбранного префикса** ошибочно считается доказательством завершённости всего ряда. Высокая карточка сразу за этим префиксом не исследуется.

Ошибка не находится в самом сравнении `nextHeight > shelfHeight`: стек действительно не должен превышать принятую высоту. Недостаточен способ принятия и проверки этой высоты перед фиксацией ряда.

В `tests/shelf-grid.test.tsx` есть тест `revisits earlier stacks when a newly admitted tall card raises the shelf`: `[40,40,100,220,50]`, три колонки. Там первая пара уже помещается в начальные 100 px, поэтому высокая четвёртая карточка допускается в ряд. Проверка не покрывает случай, когда для допуска высокой карточки сначала нужна её же высота, и не покрывает исчезновение промежуточного стека второй и третьей карточек.

На базе анализа все **47 существующих ShelfGrid-тестов проходят**. Они не опровергают найденный дефект: нужной регрессии среди них нет.

## 5. Предлагаемый контракт исправления

| ID | Требование |
| --- | --- |
| R1 | Для четырёхколоночного примера из раздела 3 оба состояния и переход в обе стороны дают `[1,2] | [3] | [4] | [5]`, высоту ряда 600 и одинаковые placements первых двух |
| R2 | Результат не зависит от истории: загрузка сразу в раскрытом состоянии даёт ту же композицию, что раскрытие после свёрнутого |
| R3 | Перед завершением ряда рассмотреть первую ещё не размещённую карточку, если её естественная высота больше текущей оценки |
| R4 | Повышение оценки до высоты этой карточки допустимо только если пробная последовательная упаковка действительно включает её и весь предшествующий префикс в текущий ряд |
| R5 | Не перепрыгивать через первую неразмещённую карточку и не брать максимум всего остатка группы. Если ближайший кандидат не подходит, завершить текущий ряд по прежнему результату |
| R6 | Пробный проход не меняет уже принятые слоты. Невозможность вместить wide-кандидата не повышает высоту и не теряет карточки |
| R7 | Сохранять порядок, группы, spans, единичные placements, отсутствие пересечений, положительную целочисленную геометрию, минимальные естественные высоты и выравнивание нижних границ |
| R8 | Сохранить одну колонку, произвольное число карточек в стеке, пользовательские gaps и точное правило границы: равенство разрешено, превышение на 1 px запрещено |
| R9 | Сохранить измерение на клоне, DOM identity, фокус, исключения визуальных мутаций и завершение очереди кадров без observer-loop |
| R10 | Реальные изменения высот по-прежнему запускают упаковку. Во время `packingFrozen` сохраняется композиция, а отложенная упаковка выполняется после снятия блокировки |
| R11 | Общий упаковщик продолжает корректно работать в `appendTailToComposition`: `minimumShelfHeight`, `columnOffset`, частичная ширина, `topOffset` закреплённого редактора и ограничения роста вправо сохраняются |
| R12 | Визуальный результат сопоставлен с описанным сценарием и доступным референсом; нет новых изменений внешнего вида, поведения прокрутки, данных или интерфейса |

Уточнение прежней спецификации затрагивает её требование 2 о выборе высоты ряда и требование 8 о результате перепаковки. Новое правило допускает локальную пробную оценку по **первой карточке на границе ряда**, а не только по уже допущенным карточкам. Высота не увеличивается произвольно ради сложения коротких карточек: её должен обеспечивать реально размещённый высокий кандидат.

Это не обещание абсолютной неподвижности всех соседей при любом изменении заметки. Если исчезла высокая опора, изменилась ширина/порядок, содержимое превысило доступную высоту либо стало возможно присоединить третью карточку к стеку, геометрия может законно измениться по действующему контракту. Здесь фиксируется случай, когда сохраняется та же допустимая композиция и та же высота ряда.

## 6. Способ исправления

### 6.1. Один пробный проход с явно заданным пределом

Выделить существующий внутренний проход по колонкам в локальную функцию `packAtHeight(limit)`. Она использует те же `items`, `heights`, `capacity`, `stackGap`, `columnOffset` и `totalColumns`; возвращает новые `slots` и `consumed`. Внешний цикл остаётся владельцем выбора высоты.

На каждом проходе:

1. Выполнить обычную упаковку при текущем пределе.
2. Если допущенные карточки подняли высоту, повторить упаковку, как раньше.
3. Если высота больше не выросла, взять `items[packed.consumed]`.
4. Если такого элемента нет или его высота не выше текущей, вернуть текущий результат.
5. Иначе попробовать упаковку при высоте этого элемента.
6. Принять повышение только при `trial.consumed > packed.consumed`. Поскольку проход всегда потребляет последовательный префикс без пропусков, это доказывает включение кандидата.
7. Повторить внешний цикл при принятой высоте. Если проба не включила кандидата, вернуть прежний результат без изменения высоты.

### 6.2. Предлагаемая реализация для будущего изменения

Ниже полный вариант замены `packShelfItems`; остальные публичные функции и формат placements сохраняются. Код представлен в плане, в приложение не внесён.

```ts
function packShelfItems(
  items: readonly ShelfTailItem[],
  heights: readonly number[],
  capacity: number,
  stackGap: number,
  columnOffset = 0,
  minimumShelfHeight = 0,
  totalColumns = capacity,
): { slots: ShelfSlot[]; consumed: number } {
  if (items.length === 0 || capacity < 1) return { slots: [], consumed: 0 };

  let baselineEnd = 0;
  let baselineColumns = 0;
  while (baselineEnd < items.length
    && baselineColumns + items[baselineEnd].columnSpan <= capacity) {
    baselineColumns += items[baselineEnd].columnSpan;
    baselineEnd += 1;
  }
  if (baselineEnd === 0) return { slots: [], consumed: 0 };

  const packAtHeight = (limit: number): { slots: ShelfSlot[]; consumed: number } => {
    const slots: ShelfSlot[] = [];
    let consumed = 0;
    let column = 0;
    while (column < capacity && consumed < items.length) {
      const item = items[consumed];
      if (column + item.columnSpan > capacity) break;
      const indexes = [item.index];
      let usedHeight = heights[item.index];
      consumed += 1;
      if (item.columnSpan === 1 && totalColumns > 1) {
        while (consumed < items.length) {
          const next = items[consumed];
          if (next.columnSpan !== 1) break;
          const nextHeight = usedHeight + stackGap + heights[next.index];
          if (nextHeight > limit) break;
          indexes.push(next.index);
          usedHeight = nextHeight;
          consumed += 1;
        }
      }
      slots.push({ column: columnOffset + column, columnSpan: item.columnSpan, indexes });
      column += item.columnSpan;
    }
    return { slots, consumed };
  };

  let shelfHeight = Math.max(
    minimumShelfHeight,
    ...items.slice(0, baselineEnd).map((item) => heights[item.index]),
  );
  while (true) {
    const packed = packAtHeight(shelfHeight);
    const nextShelfHeight = Math.max(
      minimumShelfHeight,
      ...packed.slots.map((slot) =>
        slot.indexes.reduce((total, index) => total + heights[index], 0)
        + stackGap * Math.max(0, slot.indexes.length - 1)),
    );
    if (nextShelfHeight > shelfHeight) {
      shelfHeight = nextShelfHeight;
      continue;
    }

    const boundary = items[packed.consumed];
    if (!boundary || heights[boundary.index] <= shelfHeight) return packed;
    const trialHeight = heights[boundary.index];
    const trial = packAtHeight(trialHeight);
    if (trial.consumed <= packed.consumed) return packed;
    shelfHeight = trialHeight;
  }
}
```

### 6.3. Почему решение корректно для найденного дефекта

В раскрытом состоянии первый проход останавливается на высоте 500 перед пятой карточкой. Проба с её высотой 600 складывает первые две и размещает все пять; `consumed` растёт с 4 до 5. Следующий проход подтверждает высоту 600 уже по реально включённой пятой карточке. Финальный `layoutComposition` получает ту же композицию, что в свёрнутом состоянии, поэтому первые две имеют те же размеры и позиции.

Проба не разрешает стеку превышать заданный предел и не создаёт новую высоту из суммы коротких карточек. Одиночная карточка, превышающая предел, по-прежнему допускается существующим проходом; внешний цикл затем повышает предел до фактической высоты этого слота.

При каждой продолжающей итерации высота строго увеличивается. Новую высоту задаёт фиксированный минимум либо одна из конечного набора нормализованных высот карточек: стек сам не может превысить свой предел. Поэтому цикл завершается без искусственного лимита числа итераций.

Одна проба линейна по рассмотренному префиксу. Для `m` оставшихся карточек консервативная верхняя оценка одного вызова упаковщика — `O(m²)` из-за повторных проходов. Это не заявка на глобально оптимальную упаковку всей группы. При реализации нужно измерить суммарную стоимость на длинных искусственных группах; произвольный лимит на число карточек или пропуск проверки кандидата ради скорости не вводить.

### 6.4. Почему не подходят более короткие обходы

| Вариант | Проблема |
| --- | --- |
| `Math.max` по всем оставшимся заметкам | Высокая заметка из отдалённого ряда начинает определять чужую полку; меняется модель раскладки всей группы |
| Всегда сохранять прежнюю композицию | Скрывает дефект только после удачного первого состояния; загрузка сразу раскрытого состояния остаётся неправильной, а новые короткие карточки не собираются в стеки |
| Включать freeze при любом раскрытии | Откладывает неправильную упаковку до снятия блокировки и нарушает существующий контракт реальных изменений высоты |
| Принять высоту кандидата без проверки его размещения | Особенно при wide-карточке ряд получает высоту элемента, который фактически ушёл в следующий ряд |
| Менять только CSS / `layoutComposition` | Решение о том, какие карточки находятся вместе, к этому моменту уже принято неправильно |
| Независимые колонки или сортировка по высоте | Меняют утверждённую структуру рядов и порядок чтения; для этой ошибки не требуются |
