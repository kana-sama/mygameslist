# Inline render diff

## Цель

Сделать семантику diff однозначной и компактной:

- красная строка показывает удалённое содержимое;
- зелёная строка показывает добавленное содержимое;
- обычная замена состоит из N красных и M зелёных строк;
- жёлтая строка существует только в render-mode и объединяет безопасно сопоставленную локальную правку в одну строку.

Source-mode остаётся точным представлением исходных строк и никогда не использует жёлтые объединённые строки.

## Ограничение истории

Спецификация, implementation plan, реализация, стили и тесты относятся к одной фиче и должны войти в один итоговый Jujutsu-коммит. Промежуточные коммиты для спецификации или плана не создаются.

## Текущее состояние

`createMarkdownDiff` уже:

- сохраняет точные строки до и после изменения;
- разделяет строки на `context`, `removed` и `added`;
- безопасно сопоставляет похожие строки при similarity не ниже `0.72`;
- не сопоставляет неоднозначные структурные якоря;
- создаёт `modified`-фрагменты и пословные decorations;
- сохраняет точный source fallback.

Сейчас `MarkdownDiffPreview` показывает `modified`-фрагмент как две render-стороны — старую и новую. Для таблицы это приводит к двум полным таблицам. Новая фича меняет только представление render-mode; точная доменная история и source-mode остаются источником истины.

## Выбранный подход

Используется отдельная render-only merge model поверх существующего `MarkdownDiffModel`.

`MarkdownDiffPreview` преобразует hunk в последовательность render units:

1. Контекст показывается один раз.
2. Неспаренная удалённая строка становится красной строкой.
3. Неспаренная добавленная строка становится зелёной строкой.
4. Безопасная пара старой и новой строки становится одной жёлтой inline-строкой.
5. Если структурно корректное объединение доказать нельзя, fragment сохраняется как обычные красная и зелёная стороны.

Доменная модель не создаёт синтетический Markdown и не теряет исходные строки. Merge model существует только на время render-mode.

## Правила inline-строки

Жёлтая строка допустима, когда:

- строки уже имеют общий `pairId` от существующего безопасного сопоставления;
- для многострочного fragment каждая старая физическая строка однозначно сопоставлена с одной новой;
- тип Markdown-блока и его структура позволяют использовать новую сторону как render-скелет;
- таблица сохраняет то же количество и границы колонок.

Внутри жёлтой строки:

- неизменённый контекст выводится один раз;
- замена выводится как зачёркнутый красный старый фрагмент, стрелка `→`, подчёркнутый зелёный новый фрагмент;
- локальная вставка выводит только зелёный новый фрагмент;
- локальное удаление выводит только зачёркнутый красный старый фрагмент;
- стрелка появляется только при наличии и старого, и нового фрагмента;
- строка получает жёлтый фон, жёлтую левую границу и семантический вид `modified`.

Если fragment содержит несколько безопасных пар физических строк, каждая пара становится отдельной жёлтой визуальной строкой. Если хотя бы одна строка не имеет однозначной пары, весь fragment показывается обычной группой красных и зелёных строк.

## Текст и Markdown-форматирование

Новая сторона служит структурным скелетом: заголовки, абзацы, списки, ссылки, emphasis и code продолжают рендериться существующим `MarkdownView`.

Render-only inline descriptors задают позиции и содержимое старых/новых фрагментов. `MarkdownView` вставляет visual evidence в уже разобранную структуру, не добавляя служебные маркеры в Markdown и не повторяя его парсер.

Если inline descriptor пересекает границу, которую существующий renderer не может безопасно представить — например, меняет саму структуру ссылки или code span, — используется красно-зелёный fallback.

## Чеклисты

Для смены состояния task marker:

- render-mode показывает старый disabled checkbox, стрелку и новый disabled checkbox;
- текст пункта выводится один раз по новой стороне;
- если одновременно изменён текст пункта, его локальные изменения показываются в той же жёлтой строке;
- добавленный или удалённый пункт остаётся полноценной зелёной или красной строкой.

Интерактивное изменение task state в diff остаётся отключённым.

## Таблицы

Table hunk рендерится как одна таблица:

- structural prologue и заголовки выводятся один раз;
- context rows выводятся один раз;
- неспаренные removed rows остаются красными;
- неспаренные added rows остаются зелёными;
- безопасно спаренная row выводится один раз по новой структуре и получает жёлтый фон;
- изменения текста показываются внутри соответствующей cell;
- изменение checkbox показывается внутри соответствующей cell как старое состояние `→` новое.

Для объединённой таблицы используются строки hunk в исходном diff-порядке. Paired removed row исключается, paired added row становится render-скелетом. Метаданные строк и inline descriptors переносятся на новые визуальные индексы.

Если число колонок, delimiter или row structure несовместимы, table fragment использует красно-зелёный fallback и остаётся валидным Markdown.

## Preview budget

- Обычная красная или зелёная визуальная строка расходует одну строку бюджета.
- Одна жёлтая inline-строка расходует одну строку бюджета, а не две.
- Source-mode продолжает считать точные старые и новые строки отдельно.
- Усечение не должно разделять многострочный structural fragment или терять одну сторону source-пары.

## Доступность

- Цвет всегда дополнен `data-diff-kind`, accessible name и визуальным оформлением.
- Жёлтая строка имеет accessible label `Изменено`.
- Старый inline-фрагмент имеет label `Удалено: …` и семантику удаления.
- Новый inline-фрагмент имеет label `Добавлено: …` и семантику добавления.
- Стрелка декоративна и скрыта от accessibility tree.
- Старый и новый checkbox имеют отдельные понятные labels; оба disabled.
- Source-mode сохраняет существующие точные labels строк.

## Fallback и ошибки

Любая неоднозначность приводит к более подробному, но точному представлению:

1. Нельзя доказать 1:1 pairing — красные и зелёные строки.
2. Нельзя безопасно объединить Markdown structure — красные и зелёные render-стороны.
3. Вся заметка не renderable — существующий exact source fallback.

Ни один fallback не изменяет `before`, `after`, reconstruct-функции или source-mode.

## Тестирование

Domain tests подтверждают:

- существующие pairing, reconstruction и ambiguity guarantees не изменились;
- multi-line eligibility требует полной 1:1 пары;
- несовместимая table structure получает fallback.

Component tests подтверждают:

- правка обычного текста занимает одну жёлтую строку, а общий контекст не дублируется;
- замена, вставка и удаление inline-фрагментов оформлены правильно;
- Markdown emphasis, links и code сохраняют структуру либо используют fallback;
- task toggle показывает два checkbox и одну подпись;
- одновременная правка checkbox и текста остаётся одной строкой;
- добавленные и удалённые checklist items остаются зелёными и красными;
- table hunk рендерится одной таблицей;
- modified table cell и checkbox показываются inline;
- table row additions/removals остаются внутри той же таблицы;
- multi-line paired fragment объединяется построчно;
- неполная multi-line pair использует красно-зелёный fallback;
- render preview считает жёлтую строку один раз;
- source-mode не получает жёлтых строк и остаётся точным;
- accessible names различают удалённое, добавленное и изменённое содержимое.

Финальная проверка запускает targeted tests, полный `npm test` и `npm run build`.

## Границы фичи

Фича не меняет:

- алгоритм сохранения и публикации patch;
- интерактивное редактирование Markdown;
- source diff format;
- similarity threshold `0.72`;
- правила ambiguous anchors;
- summary text вне необходимых корректировок количества visual rows.
